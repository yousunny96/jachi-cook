# 소복 개발 인계 명세서

모바일 웹 프로토타입과 출시 구현 기준

버전 1.1   2026년 10월 19일

## 문서의 목적과 기준

소복은 혼자 사는 사용자가 보유한 식재료·양념·조리 도구로 만들 수 있는 요리를 쉽게 고르는 모바일 웹앱이다. 홈은 단순한 가상 주방이며 냉장고는 재료 관리, 조리대는 도구·양념 관리, 요리책은 추천 목록으로 연결된다. 사용자가 고른 친구 캐릭터가 상황에 맞는 말풍선으로 요리를 함께한다.

이 문서는 개발자가 화면과 동작, 데이터, 예외 처리, 검수 조건을 이어서 구현할 수 있도록 정리한 인계 자료다. 인터랙티브 프로토타입은 사용자 흐름을 검토하는 산출물이며 출시용 레시피 콘텐츠와 외부 검색 서버를 완성한 제품을 뜻하지 않는다.

|---|---|
| 대화에 직접 제공한 자취생 요리 PRD v1.0 | 재료·도구·양념 관리, 추천 규칙, 상세, 요리 완료, 저장, API, 측정 기준 |
| 이후 사용자가 요청한 캐릭터 선택과 단순한 주방 | 12종 캐릭터 선택, 성격별 말풍선, 가구 중심의 단순한 홈 |

충돌할 때는 사용자의 최신 직접 요청을 우선하고, 기능은 PRD를 따른다. 이미지에 표시된 재료 8개나 음식 카드는 화면 예시이며 실제 사용자 보유 정보나 검수된 레시피로 간주하지 않는다. 이 명세서에서 **출시 요구사항**, **프로토타입 범위**, **개발 제안**을 구분한다. 개발 제안은 합의 완료를 의미하지 않는다.

## 제품 범위와 인계 상태

### 이번 프로토타입의 범위

- 홈의 냉장고·조리대·요리책과 하단 메뉴를 통해 주요 화면으로 이동한다.
- 12종 캐릭터를 미리 보고 선택하며 선택한 친구와 대사가 홈에 반영된다.
- 재료 카테고리·검색·선택, 도구 6종·양념 선택, 보유 상태에 따른 추천 그룹 변화를 확인한다.
- 요리 상세의 보유·부족 상태와 외부 검색 링크, 완료 후 선택한 재료만 제거하는 흐름을 확인한다.
- 이 브라우저에 상태를 저장하며 저장 실패 시 현재 세션에서 계속 사용할 수 있게 한다.
- 레시피 6개에 AI가 작성한 1인분 분량과 번호별 조리 단계를 제공한다. AI 초안이며 사람의 검수 완료를 의미하지 않는다.

### 출시까지 남은 범위

| 항목 | 이번 산출물의 경계 | 출시 기준 |
|---|---|---|
| 레시피 콘텐츠 | AI가 작성한 조리 단계와 분량 6개, 선택형 실시간 생성 | AI 작성 허용, 출시 전 검수한 30개, 난이도마다 최소 6개 |

로그인, 계정 동기화, 사용자 DB, 재료 수량, 유통기한, 외부 레시피 수집, 구매·결제는 이번 MVP 범위에 없다. 향후 커머스는 부족한 재료의 canonical ID를 상품과 연결하는 별도 단계로 계획한다. 현재 화면에 동작하지 않는 구매 버튼을 넣지 않는다.

### 처음부터 내 정보로 시작

S00 → S03에서 도구·양념 선택 → S02에서 재료 선택 → S01에서 추천 확인 → S06 상세 → D01 완료 확인 → S01 추천 갱신.

처음 설정에서 기본으로 보유했다고 간주하는 재료·양념·도구를 넣지 않는다. 0개도 저장할 수 있으며 해당 빈 상태 안내로 이어진다. 주방 설정을 끝냈다는 상태는 저장하되, 뒤로 이동해 수정할 수 있어야 한다. 최초 캐릭터는 하치와레이며 언제든 바꿀 수 있다.

### 예시로 둘러보기

S00의 별도 선택으로 예시 재료·양념·도구를 넣어 추천 흐름을 빠르게 확인한다. 예시 데이터가 자신의 실제 냉장고로 오해되지 않도록 시작 화면과 시연 콘텐츠에 표시한다. 예시는 사용자가 선택할 때만 불러오며 기존 사용자 상태에 자동으로 덮어쓰지 않는다. 예시 진입 후에도 재료·도구·친구를 바꿀 수 있다.

### 외부 콘텐츠와 복귀

S06에서 영상·블로그 더 보기를 누르기 전에는 외부 검색을 요청하지 않는다. 결과 또는 대체 검색 링크를 누르면 외부 서비스로 이동한다. 프로토타입은 검색 링크를 제공한다. 외부 링크를 새 탭으로 열 때 이를 접근 가능한 이름에 알리고 원래 화면의 선택·스크롤을 유지한다. 서비스에서 돌아왔다는 이유로 재료를 자동 삭제하거나 요리 완료 처리하지 않는다.

## 내 집과 캐릭터 경험

### 가구와 버튼의 관계

| 대상 | 의미 | 활성 영역과 표시 |
|---|---|---|
| 왼쪽 냉장고 | 내 식재료 | 냉장고 전체에 대응하는 실제 버튼과 내 냉장고 라벨, 선택 재료 수 |
| 오른쪽 조리대 | 내 도구·양념 | 내 주방 버튼, 도구·양념 보조 설명 |
| 작은 식탁의 요리책 | 추천 목록 | 요리책으로 이동하는 버튼과 이름 |
| 중앙 친구 | 함께하는 분위기 | 현재 캐릭터 1명과 상황 대사 1개 |
| 상단 친구 선택 영역 | 친구 변경 | 현재 이름·작은 초상·친구 바꾸기 |

냉장고는 첫 화면에서 인식 가능해야 하며 항상 접근 가능한 내비게이션으로도 열 수 있어야 한다. 화면 전체를 한 장의 이미지로 만들고 보이지 않는 좌표만 사용하는 방식은 피한다. 반응형 이미지 위의 가구 버튼도 실제 button 또는 link 요소로 제공하고 문서 순서·키보드 포커스를 유지한다.

주방은 냉장고, 짧은 조리대, 작은 식탁, 창문 위주로 단순하게 구성한다. 장식·무늬·선반을 추가해 정보 밀도를 높이지 않는다. 말풍선은 냉장고와 내 주방의 버튼을 가리지 않는다. 모바일에서 추천 결과가 아래로 이어진다는 것을 알 수 있도록 홈에 다음 구역의 제목이나 첫 카드를 노출한다.

### 친구 선택과 말풍선 규칙

S05는 3열 4행이 기준이다. 선택 중인 카드에는 외곽선과 체크 표시를 함께 보여주고, 이름과 성격을 텍스트로 제공한다. 카드를 누르면 미리보기만 바뀌며 함께하기를 누른 순간 선택을 저장한다. 뒤로 가면 이전에 적용한 친구를 유지한다. 선택은 추천 정렬·난이도·재료 판단에 영향을 주지 않는다.

말풍선은 실행 중 임의 생성하지 않고 사전에 작성한 문구 테이블로 관리한다. 출시 전 문구 검수는 별도로 진행한다. 홈 입장에는 entry, 요리를 고르는 상황에는 choose, 완료 확인 후에는 complete를 사용한다. 완료 대사는 실제 제거 확정 또는 재료 변경 없이 완료 확정한 뒤 보여준다. 체크 확인 화면을 열기만 했을 때는 완료 대사를 쓰지 않는다. 같은 상황에서 자동 타이핑·반복 팝업·음성을 강제하지 않는다.

## 재료와 주방 관리

### 재료 선택

재료는 채소, 고기·해산물, 달걀·유제품, 곡물·가공식품 등 표시 카테고리와 canonical ID를 갖는다. 카테고리는 탐색용이며 레시피 매칭 단위가 아니다. 선택한 칩을 다시 누르면 해제한다. 편집 중 선택은 임시 상태에 두고 저장 버튼을 누르면 반영한다. 저장하지 않고 나가면 기존 보유 상태를 유지한다. 중복 저장하지 않는다. 재료 수는 선택된 고유 ID 수이며 양념·도구 수를 합산하지 않는다.

검색어와 검색 대상 이름·별칭을 유니코드 NFKC로 정규화하고 공백 제거와 소문자 처리 후 비교한다. 검색어가 있으면 현재 선택 카테고리와 무관하게 전체 재료에서 검색한다. 예를 들어 채소 카테고리를 열어둔 상태에서 달걀을 검색해도 계란이 나와야 한다. 파는 대파, 달걀은 계란의 별칭으로 연결한다. 결과 선택은 별칭 문자열 대신 해당 canonical ID를 저장한다. 검색어를 지우면 기존 카테고리 화면으로 돌아간다.

검색 결과가 없으면 입력어와 재시도 안내를 표시한다. 시연 버전에서 자유 텍스트로 알 수 없는 재료를 무조건 추가하지 않는다. 출시 재료 목록 확대는 관리된 목록과 별칭 사전을 함께 갱신한다.

### 도구와 양념

| 구분 | 필수 규칙 |
|---|---|
| 도구 | 전자레인지·프라이팬·냄비·오븐·에어프라이어·전기밥솥 총 6종 |
| 보유 기준 | 도구·양념·재료 모두 있음/없음만 관리 |
| 양념 예 | 소금·식용유·간장 등 검수된 레시피 목록에 필요한 항목 |
| 저장 | 현재 브라우저에 저장, 메뉴나 설정에서 언제든 변경 |
| 변경 효과 | 도구·양념의 저장된 선택이 바뀌면 추천을 다시 계산 |
| 완료 처리 | 양념과 도구는 자동 제거 대상에서 항상 제외 |

레시피가 여러 도구를 요구하면 모두 있어야 한다. 대체 가능한 도구 그룹, 선택 재료, 대체 양념은 초기 PRD에 정의되지 않았으므로 임의로 추론하지 않는다. 출시 콘텐츠 담당자가 필요성을 결정한 뒤 데이터 구조와 매칭 규칙을 함께 변경한다.

## 추천과 상세와 완료 규칙

### 추천 계산

각 레시피 r에 대해 필요한 도구 T(r), 식재료 I(r), 양념 C(r)를 고유 ID 집합으로 다룬다. 사용자의 도구 T(u), 식재료 I(u), 양념 C(u)와 비교한다.

1. T(r)의 모든 ID가 T(u)에 있을 때만 이후 계산을 한다. 하나라도 없으면 추천 목록에서 제외한다.
2. 부족 식재료는 I(r) − I(u), 부족 양념은 C(r) − C(u)다.
3. 두 종류를 합친 부족 항목 수가 0이면 바로 만들 수 있어요에 넣는다.
4. 부족 수가 1 또는 2이면 1~2개만 사면 돼요에 넣고 부족 이름을 표시한다.
5. 부족 수가 3 이상이면 추천 목록에서 제외한다.
6. 각 그룹은 쉬움 → 보통 → 어려움, 같은 난이도는 분 단위 조리 시간 오름차순으로 정렬한다. 두 값이 같으면 recipe ID 오름차순을 안정적인 동률 규칙으로 사용한다.

식재료와 양념의 ID는 전역으로 충돌하지 않게 관리한다. 부족 수는 목록 길이를 그대로 더하기 전에 중복을 제거한다. 표시용 이름 변경은 계산에 영향을 주지 않아야 한다. 조리 시간·단계 수는 사람이 레시피의 난이도를 정하는 근거이지 보유 상태에 따라 난이도를 재산정하는 공식이 아니다.

레시피 카드에는 이름·난이도·시간·필요 도구를 보여준다. 부족 그룹에는 식재료와 양념을 구분할 수 있는 부족 항목 이름을 모두 보여주며 2개일 때 임의로 한 항목을 감추지 않는다. 난이도 필터가 있다면 위 규칙으로 얻은 결과에 필터를 적용한다. 사용자가 보유하지 않은 도구로 가능한 것처럼 보여서는 안 된다.

### 상세

상단에는 카드와 동일한 난이도·시간·도구를 표시한다. 재료와 양념은 각각 목록으로 보여주고 보유는 체크와 있음, 부족은 없음으로 구분한다. 색상만으로 상태를 전달하지 않는다. 상세를 여는 동안 주방 상태가 바뀌었다면 현재 상태로 다시 계산한다.

최신 요청에 따라 AI 조리 단계 생성을 허용한다. 상세에는 AI 작성 표시, 1인분 분량, 번호별 단계와 팁을 제공한다. 번들 초안은 API 없이 보이며 실시간 생성은 서버 키 설정 후 사용할 수 있다. 출시 전 콘텐츠 검수는 별도로 진행한다. 외부 콘텐츠의 설명을 복사해 내부 조리 단계나 난이도 판정으로 사용하지 않는다.

### 요리 완료와 냉장고 반영

완료 버튼을 누르면 레시피의 식재료 중 현재 냉장고에 있는 항목만 D01에 체크된 상태로 표시한다. 사용자는 남아 있는 재료의 체크를 해제한다. 냉장고에서 빼기를 확정하면 체크된 ID만 제거한다.

삭제 대상 = 레시피 식재료 ∩ 현재 보유 식재료 ∩ 사용자가 체크한 항목.

양념·도구·레시피와 무관한 재료·처음부터 없었던 재료는 변경하지 않는다. 체크 해제한 재료는 남는다. 취소하면 아무것도 바꾸지 않는다. 모두 체크 해제해도 재료 변경 없이 완료할 수 있다. 확인 전과 직전 상태가 달라졌다면 위 교집합을 다시 적용해 안전하게 처리한다. 확정 후에는 홈 추천과 재료 수를 갱신하고 친구의 완료 대사를 보여준다.

## 데이터 계약과 브라우저 저장

### 콘텐츠 데이터

| 데이터 | 핵심 필드와 조건 |
|---|---|
| Ingredient | 현재 id, name, category, emoji, aliases 배열. ID 고유, 별칭도 동일 ID에 연결. 출시 시 category ID 분리 검토 |
| Condiment | 현재 id, name. Ingredient와 ID 충돌 금지. 출시 시 별칭 검색이 필요하면 aliases 추가 |
| Tool | id, name. PRD의 6종으로 제한 |
| Character | 현재 id, name, personality, crop, dialogues 배열. dialogues 순서는 입장·선택·완료. 출시 자산 분리 시 asset 경로 사용 |
| Recipe | 현재 id, name, difficulty, minutes, tools, ingredients, condiments, art, steps, isDemo. 배열 값은 각 카탈로그의 ID |
| Content review | reviewedBy, reviewedAt, sourceNote 또는 편집 이력. 출시 콘텐츠만 관리 |

difficulty는 easy, medium, hard와 쉬움, 보통, 어려움 표시값을 일관되게 매핑한다. minutes는 양의 정수다. steps는 순서가 있는 텍스트 배열이며 검수된 출시 레시피에서 비어 있으면 안 된다. 모든 참조 ID는 해당 카탈로그에 존재해야 한다. 현재 데이터는 isDemo가 true이며 steps에 AI 작성 단계를 담는다. amounts는 등록 재료·양념 ID별 분량, servings는 1, water는 물 분량, tip은 조리 팁이다. recipes.production.json은 빈 배열로 두었다. 출시 데이터에는 검수 상태 필드를 추가하고 reviewed로 확인된 콘텐츠만 추천에 사용한다.

### 저장 계약

프로토타입 저장 키는 sobok.prototype.v1이다. 같은 출처의 localStorage에 선택 상태만 저장한다. 기본 데이터 구조는 다음과 같다.

```json
{
  "version": 1,
  "selectedCharacter": "hachiware",
  "tools": [],
  "condiments": [],
  "ingredients": [],
  "onboardingComplete": false
}
```

구현에 추가 시연 모드 필드가 있으면 실제 소스의 이름과 역할을 함께 인계한다. 화면·검색어·현재 카테고리·팝업 상태는 영구 저장 필수값이 아니다. 냉장고·주방 상태를 URL 쿼리나 서버 요청에 싣지 않는다.

읽기와 쓰기를 각각 예외 처리한다. JSON 파싱 실패, 구조 불일치, 지원하지 않는 버전은 기본 상태로 복구하고 설정이 초기화됐음을 알린다. 알 수 없는 재료·도구 ID는 제거하고 중복은 정리한다. 알 수 없는 캐릭터는 기본 하치와레로 복구한다. 데이터 복구 때문에 페이지 전체가 멈추면 안 된다.

브라우저 저장이 차단되거나 용량 오류가 나면 메모리 상태를 유지한다. 안내 문구는 이 브라우저에서는 저장할 수 없어 새로고침하면 설정이 사라져요처럼 결과를 설명한다. 시크릿 모드 여부를 추측해 기능을 막지 않고 실제 저장 가능 여부로 판단한다. 저장 실패 후에도 선택·추천·완료 흐름은 계속 작동해야 한다.

설정의 처음부터 내 주방 설정하기는 확인을 받은 뒤 재료·도구·양념을 비우고 주방 설정 화면으로 이동한다. 선택한 친구는 유지하며 이 사실을 확인창에 표시한다. 저장 키 sobok.prototype.v1의 상태만 갱신하고 무관한 저장 데이터는 변경하지 않는다. 여러 탭 동기화는 현재 필수 범위가 아니며 출시 전 채택 여부를 결정한다.

## 외부 미디어 연동 계약

### 현재 동작과 출시 목표

프로토타입은 API 키 없이 YouTube와 네이버 블로그 검색 링크를 제공한다. 출시용은 사용자가 상세에서 더 보기를 누른 시점에 조회 전용 서버 함수 1개를 호출한다. 양쪽 제공자를 호출하더라도 클라이언트의 공개 엔드포인트는 하나로 유지한다. 서버는 주방·냉장고·친구·개인 식별 정보를 받거나 저장하지 않는다.

아래 계약과 운영 수치는 **개발 제안**이며 현재 연동 완료 또는 사용자 확정을 의미하지 않는다.

### 요청과 응답 제안

GET /api/media?recipeId=등록된ID

서버는 등록된 레시피 ID를 허용 목록에서 확인한 후 해당 이름으로 검색한다. 요청 본문은 없다. 사용자가 입력한 자유 검색어, 재료 배열, 도구 배열, 양념 배열, 캐릭터 ID, 사용자 ID를 받지 않는다. 레시피 이름을 직접 받는 방식으로 바꿀 경우에도 등록된 이름 목록만 허용한다.

```json
{
  "recipeId": "registered-recipe-id",
  "providers": {
    "youtube": {
      "status": "ok",
      "items": [
        {
          "title": "검색 결과 제목",
          "url": "공급자가 반환한 HTTPS 주소",
          "thumbnailUrl": "공급자가 반환한 이미지 주소"
        }
      ],
      "fallbackUrl": "레시피 이름을 인코딩한 검색 주소"
    },
    "naver": {
      "status": "unavailable",
      "items": [],
      "fallbackUrl": "레시피 이름을 인코딩한 검색 주소"
    }
  }
}
```

공급자별 status는 ok, empty, unavailable, rate_limited 등으로 구분한다. 한쪽 실패로 다른 쪽 성공 결과를 버리지 않는다. 정상·부분 성공은 200 응답으로 구분하고 잘못된 ID는 400, 전체 서버 요청 제한은 429로 처리할 수 있다. 클라이언트는 HTTP 오류·네트워크 오류·응답 형식 오류에도 두 검색 링크를 직접 구성해 제공한다.

API 키는 서버 환경변수에만 둔다. 결과 제목의 HTML 표시 태그는 제거하거나 안전한 텍스트로 표시한다. URL은 HTTPS와 기대한 제공자 형식을 검증한다. 외부 링크에는 안전한 새 탭 속성을 사용한다. 어떤 외부 결과도 재료 매칭과 난이도에 영향을 주지 않는다.

### 재사용과 제한 제안

| 항목 | 초기 개발 제안 | 확정할 내용 |
|---|---|---|
| 정상 결과 재사용 | 공급자+레시피 ID별 24시간 | 공급자 정책과 콘텐츠 갱신 요구 검토 |
| 빈 결과·일시 실패 | 5분 재사용 | 장애 회복 속도·중복 호출 비용 |
| 동일 요청 병합 | 같은 키의 동시 요청 1회 | 서버리스 다중 인스턴스에서 공유 저장 방식 |
| 클라이언트 반복 클릭 | 요청 진행 중 중복 요청 안 함 | 재시도 UX와 접근성 |
| 서버 공급자 호출 제한 | 공급자별 10회/분을 초기 검토값으로 사용 | 실제 사용량·할당량·호스팅 제한 |
| 일일 호출 예산 | 실제 프로젝트 할당량의 80%에서 외부 조회 중단 검토 | 리셋 시각·캐시 제공·경보·운영자 |
| 요청 시간 제한 | 공급자별 5초, 실패 공급자만 링크 전환 | 실제 모바일 지연과 서버 실행 한도 |

호출 제한과 공유 캐시는 사용자 프로필 DB와 별개다. 캐시 키에는 레시피 ID와 공급자만 사용한다. 운영 집계는 호출 수·성공·실패 등 비개인 정보로 한정한다. 호스팅 제공자의 기본 접속 로그 보관 정책은 배포 담당자가 확인한다.

API별 한도와 정책은 프로젝트 설정과 최신 공식 문서에서 배포 시 재확인한다. PRD의 하루 약 100회 문구를 검증 없이 보장값으로 제품에 노출하거나 오래된 단위 계산으로 확정하지 않는다. 공식 참고는 [YouTube 검색 API](https://developers.google.com/youtube/data/reference/rest/v3/search/list), [YouTube API 개요](https://developers.google.com/youtube/data/getting-started), [네이버 블로그 검색 API](https://developers.naver.com/docs/serviceapi/search/blog/blog.md)다.

## 디자인과 모바일 접근성

승인된 이미지의 따뜻한 크림 배경, 브라운 글자와 윤곽선, 코랄 주요 행동, 세이지 보조 배지를 유지한다. 아래 색상은 현재 프로토타입 styles.css의 토큰이다. 승인된 이미지의 분위기를 코드로 옮긴 값이며 출시 전 글자 대비를 검수한다. 간격과 타이포그래피 항목은 구현·검수 기준이다.

| 토큰 | 시작값 또는 기준 | 적용 |
|---|---|---|
| background | #FBF7EF | 전체 배경 |
| surface | #FFFAF3 | 카드·대화상자 |
| text | #4D2C20 | 제목·본문 |
| muted | #8E7665 | 보조 설명 |
| coral | #F38F7C | 선택·주요 행동의 배경 |
| sage | #DCE7C6 | 쉬움 배지·보조 영역 |
| border | #EEDFCE | 카드 경계 |
| radius | 16 / 24 / 32px | 칩·카드·큰 패널 |
| spacing | 4 / 8 / 12 / 16 / 24 / 32px | 일관된 간격 |
| content width | 모바일 320~480px 중심 | 큰 화면에서는 가운데 정렬된 모바일 경험 |

작은 글자를 코랄 위 흰색으로 무조건 표현하지 않는다. 일반 텍스트 대비 4.5:1, 큰 텍스트 3:1을 목표로 실제 색 조합을 검수하고 필요하면 짙은 글자를 사용한다. 본문은 약 16px, 보조 글자는 12~14px 범위에서 시작하되 확대 시 자르지 않는다. 한국어 가독성을 우선하며 폰트 미설치 시 시스템 글꼴로 읽을 수 있어야 한다.

최소 터치 영역은 44×44 CSS px를 목표로 한다. 하단 메뉴와 버튼은 모바일 안전 영역을 고려하며 스크롤 마지막 항목을 가리지 않는다. 320px 화면, 가로 방향, 글자 200% 확대에서 기능을 잃지 않아야 한다. 캐릭터 카드 이름과 부족 재료가 길어지면 줄바꿈을 허용한다.

선택 칩은 aria-pressed 또는 적합한 checkbox 상태, 친구 선택은 단일 선택 의미를 제공한다. 현재 메뉴는 aria-current로 표시한다. 대화상자는 제목·닫기·포커스 이동·닫은 후 원래 버튼 복귀를 처리한다. 선택 수와 저장 상태 변화는 과도한 반복 없이 보조기술에 알린다. 장식 이미지에는 빈 대체텍스트를 쓰고 캐릭터·요리 이미지는 인접 텍스트와 중복 여부에 맞춰 대체텍스트를 정한다. 움직임이 있다면 prefers-reduced-motion에서 줄인다.

### 사용자 관찰 테스트

측정 목표는 추천 목록만 보고 다른 레시피 앱이나 검색 없이 만들 요리를 고른 비율이며, PRD의 제안 목표는 10명 중 7명 이상이다. 처음 설정을 마친 뒤 메뉴를 고르기까지 1분 이내, 도움 없는 최초 설정은 5명 중 4명 이상이 3분 이내를 목표로 둔다. 이 인원과 목표는 실제 검증 결과가 아니다.

관찰자는 초기 설정 완료, 메뉴 결정 시간, 다른 검색 사용, 실제 요리 완료 도달, 보유 재료·도구와 추천의 일치를 기록한다. 프로토타입은 검수된 조리 내용이 없으므로 실제 조리 정확도나 요리 완료율을 검증했다고 주장할 수 없다. 출시 콘텐츠 확보 후 해당 테스트를 진행한다. 서버에 개인 행동 추적을 추가하지 않고 관찰 기록과 짧은 인터뷰를 사용한다.

## 소스 인계와 실행

프로토타입은 index.html, styles.css, data.js, model.js, app.js, assets 디렉터리로 구성한 정적 웹앱이다. index.html은 진입점, styles.css는 반응형 화면·토큰, data.js는 시연 카탈로그·캐릭터, model.js는 저장·추천·재료 제거, app.js는 화면·이벤트를 맡는다. 전달 묶음의 실제 파일 목록과 실행 방법은 README를 기준으로 한다.

일반적인 로컬 실행은 배포 폴더에서 정적 서버를 열고 브라우저로 localhost 주소에 접속하는 방식이다. 의존성 설치가 없는 정적 산출물을 우선한다. Python이 있는 환경에서는 아래 예시로 열 수 있다.

```sh
python3 -m http.server 4173 --directory dist
```

브라우저에서 http://localhost:4173 을 연다. dist가 압축파일의 루트라면 해당 폴더를 --directory 인자로 지정한다. 별도 실행 스크립트가 제공된 경우 README의 정확한 명령을 우선한다. 개발 서버는 컴퓨터에서 미리보는 수단이며 자동으로 공개 배포되거나 다른 휴대폰에서 접근 가능하다는 뜻이 아니다.

프로토타입은 외부 API 키 없이 확인할 수 있어야 한다. 카탈로그는 data.js, AI 조리 초안은 recipe-drafts.js에 6개, 출시 콘텐츠 파일 recipes.production.json은 빈 배열로 제공한다. tests/model.test.cjs는 모델 동작 확인용이며 실행 결과는 별도 검증 기록을 따른다. 출시용 검색 기능은 서버 함수와 환경변수 설정을 별도로 추가한다. localStorage는 출처별로 분리되므로 포트·도메인·프로토콜이 바뀌면 기존 선택이 그대로 보이지 않을 수 있다. 검수 시 같은 주소로 재접속한다.

### 콘텐츠 인계 조건

정식 레시피 목록과 내용은 사용자 또는 지정 콘텐츠 담당자가 직접 정리한다. 30개 모두 사람이 검수하고 쉬움·보통·어려움마다 최소 6개를 확보한다. 이름, 난이도, 시간, 도구, 식재료, 양념, 번호순 단계가 필수다. 난이도 기준표에는 조리 시간·단계 수와 실제 작업 복잡도를 검토한 근거를 기록한다. AI가 초안을 작성할 수 있다. 외부 검색 결과를 자동 수집하지 않으며 출시 전 검수 여부를 기록한다.

AI 초안 6개는 검수 상태를 분리해 보관하고, reviewed 출시 콘텐츠와 섞어 배포하지 않는다. 운영 데이터 검증은 개수·분포뿐 아니라 ID 참조, 누락된 단계, 중복 레시피, 양념과 재료의 잘못된 분류를 검사한다.

### 검증 기록의 지위

최종 인계에는 실제 실행한 검증의 환경·시나리오·결과·남은 제한을 별도 기록으로 첨부한다. 이 문서의 인수 조건이나 제안 수치 자체를 테스트 통과 증거로 사용하지 않는다. 정식 콘텐츠, API 연동, 자산 결정이 끝나기 전에는 출시 준비 완료로 표시하지 않는다.

## 14. 전달 파일과 확인 방법

- sobok-prototype.html: 스타일·스크립트·이미지를 포함한 단일 파일. 브라우저에서 열고 '예시로 둘러보기'로 흐름을 확인한다. 파일 URL에서는 브라우저에 따라 저장이 제한될 수 있으며, 이때 메모리 상태로 동작한다.
- sobok-developer-handoff.zip: 분리된 소스, 이미지, 테스트, 실행 안내, 명세서와 검증 기록을 포함한다. 개발자는 dist 폴더를 정적 서버로 실행한다.
- sobok-developer-spec.docx / .md: 동일한 개발 인계 명세의 편집용 문서와 텍스트 원본이다.

캐릭터는 참고 이미지를 바탕으로 생성한 투명 배경 시트를 사용한다. 현재 대사와 시각 자산은 프로토타입용이며 출시 전 검수 대상이다. 온라인 공개 배포는 완료되지 않았으므로 전달 파일을 기준으로 검토한다.


## AI 레시피 생성 계약

2026년 10월 19일 사용자의 최신 요청으로 기존 AI 생성 금지 조건을 변경했다. 추천 후보·도구 필터·부족 재료·난이도는 기존 카탈로그 규칙을 유지하고, AI는 선택한 요리의 분량과 조리 단계만 작성한다. 최초 화면에는 미리 작성한 AI 초안을 즉시 표시한다. 이 초안은 Gemini API 실호출 결과가 아니며, 이번 제작 과정에서 AI가 작성한 내용이다.

실시간 생성은 server.cjs의 POST /api/recipe가 담당한다. 요청은 recipeId 하나만 받으며 냉장고·캐릭터·사용자 정보를 받지 않는다. 서버 환경변수 GEMINI_API_KEY가 필요하며 GEMINI_MODEL의 기본값은 gemini-2.5-flash-lite다. 키를 HTML이나 브라우저 저장소에 넣지 않는다. Node.js 22 이상에서 node server.cjs로 실행한다. 키는 서버 실행 환경에만 설정한다.

서버는 등록된 요리 이름, 재료·양념·도구 ID와 이름을 전달한다. 반환 JSON의 servings는 1, amounts의 ID 집합은 등록 재료·양념과 일치해야 하며 tools도 일치해야 한다. 단계는 3~10개, 각 500자 이하, 분량은 항목당 100자 이하로 제한한다. 이 검사는 구조와 ID의 검증이며 자유문에 숨은 추가 재료나 조리 안전성을 완전히 판별하지는 못한다. 출시 시 내용 검수가 필요하다.

성공 결과는 서버 메모리에 24시간 저장하고 같은 요청은 합친다. 서버 프로세스 전체에서 분당 5회·24시간 30회의 외부 요청 상한을 둔다. 공급자 제한이 더 낮으면 공급자 실패를 표시한다. 서버 20초·브라우저 25초 제한을 사용한다. 재시작하면 캐시와 요청 기록이 사라지므로 공개 배포 때는 공유 저장소와 인증·요청 제한으로 보강한다. 현재 서버는 로컬 검토용이며 127.0.0.1에만 바인딩한다.

API 키 없음, 한도 초과, 시간 초과, 잘못된 응답에서는 기존 레시피를 유지하고 다시 시도할 수 있게 한다. 파일로 열 때는 실시간 요청을 보내지 않고 서버 필요 안내를 표시한다. 생성 결과는 현재 탭 메모리에만 두며 새로고침하면 번들 초안으로 돌아간다. 캐시 유효 기간에는 새로 만들기를 눌러도 같은 결과를 반환할 수 있다.

Gemini 2.5 Flash-Lite의 무료 구간 제공 여부는 공식 가격표에서 확인했다. 무료 사용량은 계정·지역·모델 정책에 따라 달라지며 유료 계정에는 요금이 발생할 수 있다. 자동 유료 모델 전환은 구현하지 않는다. 실제 키가 제공되지 않아 공급자 실호출은 검증하지 않았다.
